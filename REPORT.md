## 4. Is a gain real? Noise and the gate

- **Noise between identical runs.** Haiku-v000: 17 of 91 val tasks flip between two runs (39 vs 42).
  Sonnet-v000: 6 flip (67 vs 67). A single val run cannot separate a +3 improvement from noise.
- **Gate (SPEC §3.4).** Mean of 3 val runs per side; promote only if the mean gain ≥ T₃, majority
  wins − losses ≥ 1, no easy regressions and cost per task ≤ 1.3× the parent's.
  T₃ = max(2, ⌈2·σ·√(2/3)⌉) with σ = √(F/2) from the flips F: Sonnet F = 6 → σ ≈ 1.7 → **T₃ = 3**,
  frozen in `config/gate.json` from v000.
- **Early stop.** If the candidate's first val run is more than T below the parent's mean, the
  other two runs are skipped.
- **Cost of the gate:** a val run on Sonnet ≈ $3.6, so a fully validated generation ≈ $12.5 and an
  early-stopped one ≈ $6–8.
- **Confidence in v012.** Mean gain +4.0 over v000 with T = 3; all 3 v012 runs (72 / 70 / 71) are above all 3
  v000 runs (67 / 67 / 67); majority wins 4, losses 0. The mechanism is plausible: v000 lost 12–16 val tasks per
  run to the 180 s turn limit. Moderate confidence the gain is real on val; on the holdout it depends on how
  many of its questions run long (unknown). Its cost is ×1.23 per task.
- **v013 (not promoted).** Mean +5.33 over v012, wins 6 / losses 3 and cheaper per task, but one easy task
  regressed in the majority vote; the pre-registered rule rejects that. We did not change the rule after
  seeing the result. With 3 losses against 6 wins it is a plausible improvement with a regression risk.

## 7. Train / val gap and timeouts

- **Accuracy gap.** v000 (Sonnet): 91.9 % on improve-train vs 73.6 % on val.
- **Timeouts are a val-only failure class.** On val 20 of 91 tasks run > 60 s and 12–16 hit the
  180 s turn limit — half or more of the 24 failures. On improve-train no task runs > 60 s
  (Haiku or Sonnet). An improver that learns from train trajectories cannot observe this class.
- **What the reflector may see from val.** Only gold-independent runtime telemetry of the parent
  (turns that hit `max_turn_s`, turns > 60 s, p95) — the same kind of signal as a production timeout
  rate. Val correctness, task ids and question texts reach only the gate.

## 8. What did not work

- **Stage 1 (v001, rejected at SMOKE, $3.34).** The reflector (Opus) wrote a rule about the column
  `is_refused_by_adyen` — the name used in the public original of this dataset; here the column is
  `is_refused_by_psp`. The model's knowledge of public benchmarks leaks into its proposals. Defence:
  the exact schema in the reflector prompt, and a deterministic `unknown_column` check that rejects
  such candidates before any spend. Our data and answers did not come from outside sources.
- **Thin train signal.** v000 on Sonnet gets 92 % of improve-train right: an ANALYZE sample of 40
  tasks showed 2 failures. ANALYZE now runs the whole improve split plus a second run of its hard
  part (12 failures, 2 slow successes; 0 unstable tasks — Sonnet is stable on train).
- **Reflector reply cut off (v002).** Opus with a medium thinking budget inside a 16k output limit
  stopped mid-JSON. Fixed: low thinking, 32k output, one retry asking for the complete JSON.
- **Stage 2, first two processes (v002–v006):** two reflector replies cut off mid-JSON (v002, v003), two parse failures on code fences inside skill strings (v004, v006), one rule rejected at SMOKE with fixed = 1 (v005, fraud ranking by rate). After stage 2 the SMOKE pre-filter was lowered to fixed − broken ≥ 1 and the consecutive-reject stop raised to 5; parse failures get one retry and no longer count as rejects. **The val gate and T = 3 were not changed.**
- **Two candidates killed by false pre-filters, not by the gate (stage 2, third process).** v007 (a fee-matching skill) was rejected as unknown_column on local variables of its helper code; v008 (routing max_turn_s = 300 against the val-only timeouts) was rejected at SMOKE, which runs on train where timeouts never occur. Fixed: unknown_column checks only explicit column references (`table.column`, SQL fragments) in SKILL.md; a routing candidate passes SMOKE with broken = 0. Both marked `prefilter_bug` and excluded from the reflector's negative memory so they can be proposed again. **The val gate was not changed.**
- **The improver attacked the mechanics; the problem was the reading of the question.** 10 of v000's 12
  failures on improve-train are fee-delta questions ("what delta would X pay if the relative fee of
  fee ID N changed to …"). Two candidates (v010, v011) added fee-matching skills; v011's agent used
  the skill on 10 of the 12 and produced **byte-identical answers to v000 on 11 of 12** — the skill
  reproduces the same interpretation more reliably, so SMOKE fixed 0. The disagreement with the gold
  answers is about what the delta means (which payments it covers), not about matching fee rules.
  The one hypothesis aimed at the interpretation (v001: exclude refused payments) was never tested —
  it named a column that does not exist; it is now flagged `prefilter_bug` so it can be proposed again.
- **Infrastructure bug found in stage 1:** crash recovery in every `BatchRunner` constructor re-queued
  a live run of the same process; recovery now runs once per process.
- **Own mistake:** a val run was restarted by hand on a misread status (+$3.64).
- **The literal-table leak rule also fires on code** (v014): `name = number` assignments in helper code count as pairs. It should ignore code blocks and count only dict / table literals. Same class of error as the unknown_column false positive (v007).
- **Post-hoc analysis of the v013 rejection (no rule change, no promotion).** The single easy regression is
  a task that is unstable in every version: v000 1/0/1, v012 1/0/1, v013 1/0/0 — the majority vote flipped on
  one run (2/3 → 1/3). v013's strength: 6 majority wins, 3 of them 3/3 vs 0/3; 3 losses (two hard tasks
  3/3 → 1/3 and this easy task). The no-easy-regression rule, as defined on a majority of 3 runs, reacts to
  one-run noise. We did not promote v013 by relaxing the rule after seeing the result. The honest next step:
  fix a revised rule before a run (e.g. an easy regression counts only if the task drops by ≥ 2 of 3 runs)
  and gate a fee-skill candidate with it — ~20 min and ~$13, which did not fit before the deadline.
- **v013's gain did not replicate (v015).** The same change with three fresh val runs scored 71 / 66 / 69 (mean 68.67) against v012's 71.0 — below the parent. v013's 77 / 79 / 73 were a lucky draw (winner's curse: it was picked because its runs looked good). The gate, with T and the easy-regression rule, rejected v013 correctly. It also shows that selecting a candidate after looking at its val runs needs fresh runs before any promotion.
- **Two promotions not reached.** 13 candidates in ~2 h: 5 lost to reflector/parse bugs and false pre-filters (fixed during the run), 3 rejected at SMOKE, 1 interrupted, 1 promoted, 1 (v013) rejected at the gate on the easy-regression rule. Most time and money went into finding and fixing harness bugs rather than into validated candidates.

## 9. Holdout

- **Uncertainty.** The organisers' holdout has different questions; given the train/val gap, neither
  train nor val accuracy is a reliable estimate. We report val (mean of 3) and report-holdout for
  the frozen best and do not claim more.
- **Budget.** The holdout runs on our key; $15 of the $150 are reserved (our cap is $135).
  Estimated holdout cost: v012 ≈ $0.049 per task (val) → ≈ $4.9 per 100 tasks; $92.7 remain on the key.
